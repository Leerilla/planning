# 데이터를 PRD로 정제하기

PRD는 제품을 만드는 모든 이해관계자가 같은 그림을 보기 위한 합의 문서이다. 흩어진 사용자 목소리를 코드로 옮길 수 있는 형태로 정제하는 일이 본 단계의 본질이다.

본 자료는 PRD의 본질, 5요소, 제작의 역사적 흐름, NotebookLM과 Manyfast의 역할 분담, 정제 실전을 다룬다. **시드 6번(1인 셀러 카피 생성기)**을 기준으로 prd.md와 빌드 프로젝트 환경을 손에 쥐는 것이 종착점이다.

학습 목표:

- 좋은 PRD와 나쁜 PRD를 한 문장으로 구분한다
- PRD 5요소 각각의 정의와 목적을 설명한다
- NotebookLM으로 페인포인트를 추출한다
- Manyfast로 PRD 초안을 생성하고 수정한다
- prd.md를 export해 다음 단계 입력으로 준비한다
- PRD를 기준으로 프로젝트 환경을 셋업한다

## 이론

### 1️⃣ PRD란 무엇인가

이 챕터를 학습한 뒤 다음을 할 수 있다.

- PRD의 본질을 한 문장으로 설명한다
- 모호함이 만드는 임의 해석을 인식한다
- 명확한 PRD와 안티패턴을 구분한다

### PRD의 정의

PRD(Product Requirements Document)는 **제품을 만드는 모든 이해관계자가 같은 그림을 보게 만드는 합의 문서**이다.

핵심 단어는 **합의**이다.

::: aside
이해관계자에는 PM·개발자·디자이너·경영진·미래의 본인·그리고 최근에 추가된 AI 에이전트가 모두 포함된다.
:::

### 첫 단정

> **PRD는 같은 그림을 공유하기 위해 명확해야 한다.**
> 

이 단정의 본질은 PRD가 *누구를 위해* 명확해야 하는가가 아니라 *왜* 명확해야 하는가에 있다.

### PRD의 본질은 명확성

PRD가 명확해야 하는 이유는 모호함이 **임의 해석을 낳기 때문**이다.

| 모호함 | 임의 해석 주체 | 결과 |
| --- | --- | --- |
| "쉽고 편리한 도구" | 개발자 | 본인이 생각하는 쉬움 |
| "사용자 친화적 UI" | 디자이너 | 본인 취향의 UI |
| "빠른 응답" | AI 에이전트 | "빠름" 정의 없이 임의 코드 |

::: aside
AI 에이전트는 모호함의 결과를 더 빨리 드러내는 존재일 뿐이다. 인간 개발자는 질문을 던지지만, AI는 즉시 임의 해석해 결과물로 출력한다.
:::

### 명확한 PRD의 효과

| 측면 | 모호한 PRD | 명확한 PRD |
| --- | --- | --- |
| 이해관계자 해석 | 각자 다르게 | 모두 같은 그림 |
| 빌드 사이클 | 재작업 반복 | 한 번에 의도대로 |
| 검증 가능성 | 무엇이 성공인지 불명 | 측정 가능한 기준 |
| 변경 추적 | 무엇이 바뀌었는지 모름 | 변경점이 명확 |

### 안티패턴 vs 명확한 PRD

사례: 같은 도구를 두 방식으로 정의하면.

안티패턴:

```
"쉽고 편리한 카피 생성 도구를 만들어줘"
```

👉 "쉬움", "편리함"의 기준이 없어 모든 이해관계자가 임의 해석.

명확한 PRD:

```
"월 매출 100-500만원 1인 스마트스토어 셀러가
 상품 사진과 키워드 5개를 입력하면
 5초 이내에 차별화 카피 3개 후보를 받는 웹 도구"
```

👉 페르소나·입력·시간 기준·출력 개수 모두 명시.

### 1️⃣ 챕터 용어 해설

| 용어 | 정의 |
| --- | --- |
| PRD | 모든 이해관계자가 같은 그림을 보게 하는 합의 문서 |
| 이해관계자 | PM, 개발자, 디자이너, 경영진, AI 에이전트 등 |
| 합의 문서 | 모든 이해관계자가 같은 해석을 갖도록 명시 |
| 모호함 | 측정 불가능한 표현. 임의 해석을 낳음 |
| 임의 해석 | 모호한 표현을 각자 본인 기준으로 채우는 현상 |

### 2️⃣ 좋은 PRD의 5요소

이 챕터를 학습한 뒤 다음을 할 수 있다.

- PRD 5요소를 나열한다
- 각 요소의 정의와 목적을 설명한다
- 시드 6번 기준으로 5요소를 채울 수 있다

### 5요소 한눈에 보기

좋은 PRD는 5가지 요소를 갖는다. 다섯 요소 중 하나라도 비면 PRD가 아니라 메모이다.

| # | 요소 | 한 줄 설명 |
| --- | --- | --- |
| 1 | 문제 | 누가 어떤 상황에서 무엇을 어려워하는가 |
| 2 | 페르소나 | 그 문제를 겪는 사용자는 누구인가 |
| 3 | 핵심 기능 | 그 문제를 어떻게 푸는가 (3개 이하) |
| 4 | 성공 지표 | 문제 해결을 어떻게 측정하는가 |
| 5 | 제약사항 | 의도적으로 하지 않는 것은 무엇인가 |

### 요소 1 정의와 목적: 문제

문제는 **PRD의 출발점**이다. 무엇을 위해 이 제품이 존재하는지의 핵심 질문에 답한다.

목적:

- 모든 후속 결정의 기준점 제공
- 빌드 중간에 *"이 기능이 필요한가?"* 판단 기준
- 검증 단계에서 *"문제가 해결됐는가?"* 측정 기반

### 요소 1 양식과 예시: 문제

빈 양식:

```
[누가] {페르소나}가
[어떤 상황에서] {상황}
[어떤 어려움]을 겪는다
```

채워진 예시 (시드 6번):

```
[누가] 월 매출 100-500만원 1인 스마트스토어 셀러가
[어떤 상황에서] 신규 상품 등록 시
[어떤 어려움] 카피 차별화 부족으로 검색 노출 순위가 하락한다
```

### 요소 2 정의와 목적: 페르소나

페르소나는 **문제를 겪는 사용자의 구체적 윤곽**이다. 이전 단계 가설 페르소나 6줄이 그대로 들어간다.

목적:

- 기능 우선순위 결정 시 *"이 페르소나가 쓸까?"* 판단 기준
- UI/UX 결정 시 페르소나 환경 점검
- 검증 인터뷰 대상 선정 기준

### 요소 2 양식과 예시: 페르소나

빈 양식:

```
- 직군/역할
- 환경 조건
- 도구 사용
- 동기/목표
- 페인포인트 빈도
- 검증 가능 채널
```

채워진 예시 (시드 6번):

```
- 직군/역할: 월 매출 100-500만원 1인 스마트스토어 셀러
- 환경 조건: 한 달 신규 상품 5-20개 등록, 본업 병행
- 도구 사용: 스마트스토어 센터, 포토샵/캔바, 데이터랩
- 동기/목표: 광고비 의존도 낮추고 매출 다각화
- 페인포인트 빈도: 주 3-5건 등록 → 주 5-10시간 소요
- 검증 가능 채널: 네이버 카페 셀러스쿨, 셀러허브
```

### 요소 3 정의와 목적: 핵심 기능

핵심 기능은 **문제를 직접 푸는 작동의 단위**이다. MVP에서는 3개 이하로 좁힌다.

목적:

- 빌드 범위의 명시 (4개 이상은 시간 부족)
- 검증 단위의 정의
- 우선순위 명시

::: aside
입력 1 + 핵심 처리 1 + 출력 1의 3개 구성이 MVP의 표준 골격이다.
:::

### 요소 3 양식과 예시: 핵심 기능

표준 3개 구성:

```
- 기능 1 (입력): 사용자가 무엇을 입력하는가
- 기능 2 (핵심 처리): 가장 강한 페인포인트 해결
- 기능 3 (출력): 결과를 어떻게 출력하는가
```

채워진 예시 (시드 6번):

```
- 기능 1 (입력): 상품 사진 업로드 + 핵심 키워드 5개 입력
- 기능 2 (핵심 처리): 카테고리별 차별화 카피 3개 후보 생성
- 기능 3 (출력): 스마트스토어 형식 텍스트 출력
```

### 요소 4 정의와 목적: 성공 지표

성공 지표는 **제품이 의도대로 작동하는지 측정 가능한 기준**이다. 측정 불가능하면 지표가 아니다.

목적:

- 빌드 후 검증 단계의 측정 기준
- 다음 사이클 우선순위 결정
- 이해관계자 간 성공 합의 기준

### 요소 4 양식과 예시: 성공 지표

빈 양식:

```
[Before] {현재 상태의 수치}
[After] {기대하는 수치}
[측정 방법] {어떻게 측정할 것인가}
```

채워진 예시 (시드 6번):

```
지표 1: 카피 작성 시간
[Before] 상품당 평균 1-2시간 (수동 작성)
[After] 상품당 5분 이내 (도구 사용 후)
[측정 방법] 사용자 10명 인터뷰로 평균 측정

지표 2: 카피 후보 사용률
[Before] 외주 또는 경쟁사 모방 (차별화 0%)
[After] 도구 생성 후보 3개 중 1개 이상 사용 (70%)
[측정 방법] 도구 사용 로그
```

### 요소 4 잘못된 예시

| 잘못된 지표 | 왜 안 되는가 |
| --- | --- |
| "사용자 만족도 향상" | 측정 방법 없음 |
| "더 빠른 응답" | 얼마나 빠른지 기준 없음 |
| "많은 셀러가 사용" | "많은"의 기준 없음 |

### 요소 5 정의와 목적: 제약사항

제약사항은 **의도적으로 하지 않는 것 또는 외부 한계**이다. 무엇을 *하지 않을지*를 명시하는 것이 핵심.

목적:

- AI 에이전트/개발자의 임의 기능 추가 방지
- 빌드 범위의 명확한 경계선
- 다음 사이클 추가 후보 목록

### 요소 5 양식과 예시: 제약사항

빈 양식:

```
[기술 제약] 어떤 기술 스택을 사용하지 않는가
[기능 제약] 본 MVP에서 제외하는 기능
[리소스 제약] 사용 가능한 시간·비용·인원
```

채워진 예시 (시드 6번):

```
[기술 제약]
- 모바일 앱 지원 안 함 (웹만)
- 이미지 자동 생성 안 함 (텍스트만)

[기능 제약]
- 다국어 지원 안 함 (한국어만)
- 광고 자동 집행 안 함
- 경쟁사 카피 자동 분석 안 함

[리소스 제약]
- 빌드 기간 2주
- LLM API 비용 월 10만원 이내
```

### 5요소가 비면 일어나는 일

| 요소 누락 | 결과 |
| --- | --- |
| 문제 누락 | 후속 결정의 기준점 없음 |
| 페르소나 누락 | 기능 우선순위가 직감에 좌우 |
| 핵심 기능 누락 | 빌드 범위 불명. 시간 초과 |
| 성공 지표 누락 | 검증 단계에서 무엇을 측정할지 불명 |
| 제약사항 누락 | 에이전트가 임의 기능 추가 |

### 2️⃣ 챕터 용어 해설

| 용어 | 정의 |
| --- | --- |
| 5요소 | 문제, 페르소나, 핵심 기능, 성공 지표, 제약사항 |
| 성공 지표 | 제품이 의도대로 작동하는지 측정 가능한 기준 |
| 제약사항 | 의도적으로 하지 않는 것 또는 외부 한계 |
| MVP | 검증 가능한 최소 기능 제품. 핵심 기능 3개 이하 |
| 표준 3개 구성 | 입력 1 + 핵심 처리 1 + 출력 1 |

### 3️⃣ PRD는 어떻게 만들어져 왔는가

이 챕터를 학습한 뒤 다음을 할 수 있다.

- PRD 제작의 시대별 변화를 설명한다
- 분석과 정제의 차이를 인식한다
- 두 도구 분담의 역사적 정당성을 이해한다

### PRD 제작의 3시대

| 시대 | 분석 | 정제 | 한계 |
| --- | --- | --- | --- |
| 과거 (~2022) | PM이 직접 자료 읽기 | PM이 직접 작성 | 시간 소요, 편향 |
| 과도기 (2023-2024) | PM + 일반 LLM | PM + 일반 LLM | 환각, 일관성 부족 |
| 현재 (2025~) | 출처 기반 AI (NotebookLM) | 기획 전용 AI (Manyfast) | 도구 분리 필요 |

### 과거: PM이 모든 것을 직접

과거에는 PM이 분석부터 정제까지 모두 직접 처리했다.

작업 흐름:

- 사용자 인터뷰 녹음 듣기
- 노트에 받아 적기
- 페인포인트 패턴 추출
- PRD 양식 정형화
- 5요소 각각 작성

### 과거의 한계

| 한계 | 의미 |
| --- | --- |
| 시간 소요 | PRD 1건에 1-2주 |
| 분석자 편향 | 본인이 보고 싶은 패턴만 추출 |
| 일관성 부족 | 매번 양식이 달라짐 |

### 과도기: 일반 LLM의 등장

ChatGPT, Claude 같은 일반 LLM이 등장하면서 PM들은 일반 LLM에 *"이 인터뷰 자료에서 페인포인트 5개를 뽑아줘"* 같은 요청을 하기 시작했다.

분석 시간은 줄었지만 새로운 문제가 발생.

### 과도기의 새로운 문제

| 문제 | 의미 |
| --- | --- |
| 환각 | 자료에 없는 내용을 LLM이 만들어냄 |
| 출처 불분명 | 어떤 데이터에서 그 결론이 나왔는지 추적 불가 |
| 양식 불일치 | 같은 LLM도 매번 다른 양식 |
| 맥락 혼합 | LLM 학습 데이터와 본인 데이터가 섞임 |

::: aside
"스마트스토어 셀러의 78%가 카피 작성에 30분을 쓴다" 같은 통계를 LLM이 만들어내면 작업자가 검증 없이 PRD에 옮기는 사고가 자주 일어났다.
:::

### 현재: 두 도구의 역할 분담

분석과 정제는 *사고 작업의 종류*가 다르다.

| 사고 작업 | 분석 | 정제 |
| --- | --- | --- |
| 본질 | 흩어진 데이터에서 패턴 추출 | 패턴을 합의 문서로 정형화 |
| 입력 | 1차 자료 | 페인포인트 + 페르소나 |
| 출력 | 페인포인트 5개 + 출처 | 5요소 갖춘 PRD |
| 필요 능력 | 자료 안에서 답하기, 출처 인용 | 양식 일관성, 누락 검출 |

::: aside
한 도구로 두 작업을 모두 처리하면 둘 다 흐려진다. 분석 도구로 정제하면 양식이 일관되지 않고, 정제 도구로 분석하면 노이즈가 PRD에 반영된다.
:::

### 두 번째 단정

> **분석은 NotebookLM, 정제는 Manyfast이다. 두 도구의 역할은 섞지 않는다.**
> 

### 4️⃣ NotebookLM과 Manyfast 활용

이 챕터를 학습한 뒤 다음을 할 수 있다.

- 두 도구의 특징과 장점을 구분한다
- 두 도구를 나누어 활용하는 효과를 설명한다
- 시드 6번에서 각 도구를 어떻게 쓰는지 이해한다

### 도구 소개

| 도구 | 제작 | 용도 | URL |
| --- | --- | --- | --- |
| NotebookLM | Google | 출처 기반 자료 분석 | [notebooklm.google.com](http://notebooklm.google.com/) |
| Manyfast | 한국 스타트업 | PRD/기능명세/와이어프레임 생성 | [manyfast.io](http://manyfast.io/) |

### NotebookLM의 특징

| 특징 | 일반 LLM과의 차이 |
| --- | --- |
| 자료 갇힘 | 업로드한 자료 안에서만 답함 |
| 출처 인용 | 모든 답변에 인용 번호 |
| 다중 소스 통합 | CSV, PDF, 웹 링크, 텍스트 동시 처리 |
| 노트북 단위 보존 | 같은 노트북에 답변 누적 |

### NotebookLM의 장점

- 환각 거의 없음 (자료 밖 답변 안 함)
- 검증 자연스러움 (인용 클릭이 기본 동작)
- 다음 단계 재사용 (마지막 노출 단계에서 재오픈)

::: aside
본인이 모은 데이터 50-200건은 1차 자료다. ChatGPT는 학습 지식과 섞어버리지만 NotebookLM은 자료 안에서만 답한다.
:::

### Manyfast의 특징

| 특징 | 일반 LLM과의 차이 |
| --- | --- |
| 4 in 1 통합 | PRD, 기능명세, 유저플로우, 와이어프레임 한 프로젝트 |
| Claude Code MCP 연동 | Claude Code가 프로젝트를 직접 조회 |
| 한국어 네이티브 | 영어 도구의 번역체 어색함 없음 |
| AI 자동 검토 | 누락·모호한 표현 자동 지적 |

### Manyfast의 장점

- 양식 일관성 (PRD 5요소 자동 정형화)
- 동기화 자동 (PRD 수정 시 기능명세에 자동 반영)
- 빌드 연결 (Claude Code MCP로 코드 작업에 바로 연결)

### 효과 1: 사고 자원 절약

작업자가 *"이 단계에서 무엇을 기대해야 하는가"*의 판단이 단순해진다.

| 단계 | 도구 | 기대하는 산출물 |
| --- | --- | --- |
| 1 | NotebookLM | 검증된 페인포인트 5개 + 출처 |
| 2 | Manyfast | 5요소 갖춘 PRD 초안 |

NotebookLM에서 *"성공 지표를 어떻게 정해야 하는가"*를 고민하지 않는다. 그건 Manyfast의 영역이다.

### 효과 2: 검증 절차의 자연스러움

각 도구가 서로 다른 검증 절차를 자연스럽게 유도한다.

| 도구 | 검증 절차 |
| --- | --- |
| NotebookLM | 인용 클릭 → 원문 확인 |
| Manyfast | 모호한 표현 직접 수정 |

같은 도구로 두 작업을 처리하면 어느 한 쪽 검증이 느슨해진다.

### 효과 3: 결과의 추적 가능성

데이터에서 빌드 명령까지 추적 가능한 사슬이 만들어진다.

```
원본 데이터 (CSV, 인터뷰)
    ↓ [NotebookLM]
페인포인트 5개 + 출처 인용
    ↓ [Manyfast]
PRD 5요소
    ↓ [Export prd.md]
빌드 명령
```

::: aside
이 사슬이 끊어지지 않으면 PRD가 변경됐을 때 왜 변경됐는지를 원본 데이터까지 추적할 수 있다.
:::

### 효과 4: 다음 단계 연결

두 도구의 출력이 다음 단계의 입력으로 연결된다.

- NotebookLM 노트북 → 마지막 노출 단계에서 재오픈
- Manyfast 프로젝트 → 빌드 단계 prd.md 연동
- [prd.md](http://prd.md/) export → 빌드 환경 컨텍스트

### 두 도구 분담 정리

| 영역 | 분석 (NotebookLM) | 정제 (Manyfast) |
| --- | --- | --- |
| 사고 작업 | 패턴 추출 | 합의 문서 정형화 |
| 입력 | CSV, 인터뷰 응답 | 요약, 페르소나 |
| 출력 | 페인포인트 + 출처 | PRD + 기능명세 + 와이어 |
| 검증 방식 | 인용 클릭 → 원문 | 모호한 표현 직접 수정 |
| 다음 단계 연결 | 노트북 재오픈 |export |

### 안티패턴 vs 올바른 활용

안티패턴:

```
"ChatGPT한테 다 시키면 되는데
 NotebookLM이 왜 따로 필요해?"
```

올바른 활용:

```
"1차 자료 분석은 NotebookLM,
 정제는 Manyfast.
 도구의 역할을 섞지 않는다."
```

결론: 환각 위험과 출처 추적 불가능을 무시하면 PRD의 신뢰도가 흔들린다.

### 4️⃣ 챕터 용어 해설

| 용어 | 정의 |
| --- | --- |
| NotebookLM | Google의 출처 기반 AI 노트북 |
| Manyfast | 한국제 AI 기획 에디터 |
| 환각 | LLM이 학습 데이터에 없는 내용을 만들어내는 현상 |
| 분석과 정제의 분리 | 한 도구로 두 작업을 처리하면 둘 다 흐려진다 |

### 5️⃣ PRD 정제의 실전

이 챕터를 학습한 뒤 다음을 할 수 있다.

- 4단계 정제 워크플로를 실행한다
- AI 자동 검토의 한계를 인식한다
- MVP의 핵심 기능 3개 구성을 적용한다

### 4단계 정제 워크플로

| 단계 | 작업 | 도구 |
| --- | --- | --- |
| 1 | 데이터 업로드 | NotebookLM |
| 2 | 페인포인트 추출 | NotebookLM |
| 3 | PRD 생성 | Manyfast |
| 4 | 검토와 수정 | 작업자 (직접) |

### 1단계 데이터 업로드

이전 단계 자료를 NotebookLM 노트북에 업로드한다.

업로드 자료:

- 스크래핑 CSV (50-200건)
- 인터뷰 응답 텍스트 (있으면)
- 페르소나 1차 가설 워크시트

::: aside
노트북 이름은 본인 프로젝트 이름과 일치시킨다. 마지막 노출 단계에서 같은 노트북을 재오픈한다.
:::

### 2단계 페인포인트 추출

NotebookLM에 두 가지 핵심 질문을 던진다.

질문 1:

```
이 자료에서 가장 자주 등장하는 불만은 무엇인가?
출처 인용과 함께 답해줘.
```

질문 2:

```
이 사람들이 현재 어떤 방식으로
이 문제를 해결하고 있는가?
```

답변에서 인용을 클릭해 원문을 확인.

### 3단계 PRD 생성

Manyfast에 새 프로젝트를 생성하고 두 입력을 넣는다.

- NotebookLM 요약 (페인포인트 5개 + 현재 대안)
- 이전 단계 페르소나 6줄 가설

"PRD 생성" 버튼으로 초안 받기.

::: aside
초안에는 모호한 표현과 검증 불가 지표가 한 개 이상 들어 있다고 가정한다.
:::

### 4단계 검토와 수정

생성된 PRD에서 다음을 직접 수정한다.

- 모호한 표현 1개 이상 → 명확한 표현
- 검증 불가 지표 1개 → 측정 가능한 지표
- 핵심 기능 4개 이상 → 3개 이하로 좁힘
- 나머지 기능 → "제약사항: MVP에서 제외"

### AI 자동 검토의 한계

Manyfast의 AI 자동 검토는 누락된 기능과 모호한 표현을 지적한다. 그러나 다음 한계를 갖는다.

| 한계 | 의미 |
| --- | --- |
| 의도 구분 불가 | 의도한 모호함과 의도하지 않은 모호함 구분 못 함 |
| 맥락 무시 | 페르소나 특수성 반영 못 함 |
| 놓치는 모호함 | 표면적 모호함만 잡고 깊은 모호함 놓침 |

### 세 번째 단정

> **AI 자동 검토를 그대로 신뢰하지 않는다. 작업자가 직접 PRD를 읽고 모호한 표현을 찾는다.**
> 

### PRD 검토 5개 점검

5개 점검을 통과한 PRD만 prd.md로 export한다.

- [ ]  페르소나 6줄이 짧고 구체적인가
- [ ]  핵심 기능이 3개 이하인가
- [ ]  각 기능에 검증 가능한 성공 지표가 있는가
- [ ]  제약사항이 명시됐는가
- [ ]  모호한 표현이 0건인가

### MVP의 핵심 기능 3개

| 기능 개수 | 평가 |
| --- | --- |
| 1개 | ❌ 검증 단위 너무 작음 |
| 2-3개 | ✅ 적정 균형 |
| 4개 이상 | ❌ 빌드 시간 부족 |

### 표준 3개 구성

```
[기능 1] 입력 기능
    ↓
[기능 2] 핵심 처리 (가장 강한 페인포인트 해결)
    ↓
[기능 3] 출력 기능
```

### 시드 6번 3개 구성

| # | 기능 | 페인포인트 매핑 |
| --- | --- | --- |
| 1 | 상품 사진 + 키워드 입력 | 입력 단계 |
| 2 | 카테고리별 차별화 카피 3개 생성 | 차별화 (가장 강함) |
| 3 | 스마트스토어 형식 텍스트 출력 | 출력 단계 |

### 안티패턴 vs 올바른 운영

안티패턴:

```
"Manyfast가 만든 PRD를 그대로 사용한다"
```

올바른 운영:

```
"Manyfast가 만든 PRD에서 모호한 표현 1개,
 검증 불가 지표 1개를 직접 찾아 수정한 뒤 사용"
```

결론: AI 자동 검토는 작업자 검증의 보조일 뿐이다.

### 5️⃣ 챕터 용어 해설

| 용어 | 정의 |
| --- | --- |
| MVP | 검증 가능한 최소 기능 제품 |
| 검증 가능한 지표 | Before/After 수치 있는 측정 가능 형태 |
| [prd.md](http://prd.md/) export | Manyfast 마크다운 내보내기 |
| 4단계 정제 워크플로 | 업로드 → 추출 → 생성 → 검토 |
| 표준 3개 구성 | 입력 1 + 핵심 처리 1 + 출력  |

사례: 시드 6번 페인포인트 추출 결과.

```
1. 카피 차별화 부족 → 검색 노출 순위 하락 (출처 [3], [7])
```
