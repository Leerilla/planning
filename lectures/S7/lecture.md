# 통합 디버깅과 E2E 테스트

빌드한 것이 PRD대로 동작한다는 *증거*를 만드는 단계. "동작한다"는 작업자의 직감이 아니라 테스트가 통과한다는 객관 사실.

자료 6 종료 시점에 화면 2개가 동작하고 자동화 도구(sub-agent 2개, hook 2개)가 안정 작동 중. 그런데 *"화면별 동작"*과 *"시나리오 통과"*는 다른 차원. 사용자가 화면 1 → 화면 2를 끝까지 통과할 수 있는가? 본 자료가 그 질문에 답한다.

본 자료는 테스트 3단계, Playwright MCP와 자율 디버깅 3원칙, docs/prd.md 기반 시나리오 검증 루프를 다룬다. 시드 6번(1인 셀러 카피 생성기) 기준. 작업 폴더는 planning_project 그대로.

학습 목표:
- 단위·통합·E2E 테스트의 차이를 한 문장으로 구분
- 자연어로 E2E 테스트 시나리오 작성 + Playwright MCP 실행
- 자율 디버깅 3원칙(에러 그대로, 분석 먼저, 결과 검증) 적용
- docs/prd.md 기반 시나리오 검증 루프 진행

## 이론

### 1️⃣ 통합 테스트와 E2E

이 챕터를 학습한 뒤 다음을 할 수 있다.
- 3가지 테스트 단계를 구분한다
- 시나리오 통과가 동작의 정의임을 인식한다
- 화면별 동작과 시나리오 통과의 차이를 설명한다

#### 자료 6 종료 상태와 본 단계의 본질

```
[자료 6 끝 손에 있는 것]
- 동작하는 화면 2개 (카피 입력 + 카피 결과)
- prd-reviewer + git-committer 두 sub-agent
- PostToolUse + Stop 두 hook
- 병합된 PR 9개

[미확인 사항]
- 화면 1 → 화면 2 시나리오가 끝까지 통과하는가?
- 사용자가 입력부터 결과까지 한 흐름으로 완수하는가?
```

::: aside
화면별 동작은 확인됐지만 *시나리오 통과*는 별개의 검증. 본 단계가 그 빈자리를 채운다.
:::

#### 첫 단정

> **동작한다의 정의는 테스트가 통과한다이다.**

#### 3가지 테스트 단계

| 단계 | 검증 대상 | 본 학습 합격선 |
| --- | --- | :---: |
| 단위 테스트 | 한 함수 | 보조 |
| 통합 테스트 | 여러 모듈 연결 | 보조 |
| E2E 테스트 | 사용자 시나리오 | **핵심** |

#### 단위 테스트

**Unit Test**: 한 함수가 올바른 값을 반환하는지 검증.

```
"이 함수에 입력 A를 주면 출력 B가 나오는가"
```

::: aside
가장 작은 단위. 빠르게 실행. 하지만 전체 흐름은 알 수 없다.
:::

#### 통합 테스트

**Integration Test**: 여러 모듈이 합쳐졌을 때 데이터 흐름이 정상인지 검증.

```
"이 화면에서 저 화면으로 데이터가 잘 넘어가는가"
```

::: aside
단위보다 큰 범위. 모듈 간 연결 확인.
:::

#### E2E 테스트

**End-to-End Test**: 사용자가 처음부터 끝까지 시나리오를 완수할 수 있는지 검증.

시드 6번 예시:
```
"셀러가 카피 입력 화면에 상품 사진과 키워드 5개를 입력하고
 '카피 생성' 버튼을 클릭하면 결과 화면에
 차별화 카피 3개가 표시된다"
```

::: aside
가장 큰 범위. 실제 사용자 경험 시뮬레이션.
:::

#### 시나리오 통과 vs 화면 떰

작업자가 헷갈리는 부분:
> "화면이 떴으면 동작하는 것 아닌가?"

답: 화면이 떠도 시나리오 통과는 별개.

| 화면 떰 | 시나리오 통과 |
| --- | --- |
| 카피 입력 화면 렌더링 OK | 입력 → 결과 화면 라우팅 OK |
| 결과 화면 렌더링 OK | 데이터가 화면 간 정상 전달 |
| 각 화면 단독 동작 | 전체 흐름 한 번에 통과 |

#### 안티패턴 vs 통합 검증

안티패턴:
```
"각 화면이 따로따로 동작하니까 전체도 동작할 거야"
→ 통합 검증 누락
```

통합 검증:
```
"입력 화면에서 결과 화면이 한 흐름으로 통과하는지
 E2E 테스트로 증명한다"
```

#### 1️⃣ 챕터 용어 해설

| 용어 | 정의 |
| --- | --- |
| 단위 테스트 | 한 함수가 올바른 값을 반환하는지 검증 |
| 통합 테스트 | 여러 모듈 연결 시 데이터 흐름이 정상인지 |
| E2E 테스트 | 사용자가 처음부터 끝까지 시나리오 완수 |
| 시나리오 통과 | 화면 떰과 다른 차원의 검증. 동작의 진짜 정의 |
### 2️⃣ Playwright MCP와 자율 디버깅 3원칙

이 챕터를 학습한 뒤 다음을 할 수 있다.
- Playwright MCP의 사용 흐름 4단계를 외운다
- 자율 디버깅 3원칙을 본인 명령에 적용한다
- 무한 루프에 빠졌을 때 멈추는 법을 안다

#### Playwright의 정체

**Playwright**: 브라우저 자동화 도구. 코드로 사람처럼 브라우저 조작. 클릭, 입력, 페이지 이동 자동화.

#### Playwright MCP

**Playwright MCP**: Claude Code가 Playwright를 자연어로 조작하는 통합.

::: aside
시나리오를 자연어로 설명 → 테스트 코드 생성 → 실행까지. 작업자가 테스트 코드를 직접 작성하지 않는다.
:::

#### Playwright MCP 사용 흐름 4단계

| 단계 | 작업 |
| :---: | --- |
| 1 | PRD에서 핵심 시나리오 1개 선택 |
| 2 | 자연어로 시나리오 설명 → 테스트 코드 생성 |
| 3 | 테스트 실행과 통과 여부 확인 |
| 4 | 실패 시 자율 디버깅 3원칙 적용 |

#### 1단계: 시나리오 선택

사용자가 처음부터 끝까지 거치는 흐름 1개.

시드 6번 예시:
```
"셀러가 카피 입력 화면에 상품 사진과 키워드 5개를 입력
 → '카피 생성' 버튼 클릭
 → 결과 화면에서 차별화 카피 3개 확인
 → 복사 버튼으로 카피 1개 클립보드에 복사"
```

#### 2단계: 자연어 테스트 작성

```
PRD의 핵심 시나리오를 E2E 테스트로 만들어줘:
"셀러가 카피 입력 화면에 상품 사진과
 키워드 5개를 입력하고 '카피 생성' 버튼을 클릭하면
 결과 화면에 차별화 카피 3개가 표시된다"

Playwright MCP로 테스트 코드 작성과 실행까지 해줘.
```

::: aside
테스트 코드를 직접 작성하지 않음. 시나리오만 자연어로.
:::

#### 3단계: 실행과 결과 확인

```
[통과] → 다음 검증으로
[실패] → 자율 디버깅 루프로
```

#### 두 번째 단정

> **자율 디버깅 3원칙: 에러 그대로 전달, 분석 먼저, 결과 검증.**

#### 자율 디버깅이란

**Autonomous Debugging**: 에이전트가 에러 분석 → 수정 → 재실행을 반복하는 흐름.

```
작업자 = 명령자
에이전트 = 디버깅 수행자
```

#### 원칙 1: 에러를 그대로 전달

| 안티패턴 | 올바른 운영 |
| --- | --- |
| 작업자가 에러 요약 | 풀 메시지 그대로 복사 |
| "안 돼요" | 전체 스택 트레이스 |
| "에러 났어요" | 파일 경로, 라인 번호 포함 |

::: aside
에러 메시지가 길고 무서워 보여도 그대로. 요약하면 에이전트가 무엇이 문제인지 모름.
:::

#### 원칙 2: 분석을 먼저, 수정은 그다음

```
"분석해주세요"부터
       ↓
[작업자가 분석 결과 검토]
       ↓
"수정해주세요"로 이어감
```

::: aside
"고쳐주세요" 바로 → 에이전트 추측. "분석 → 수정" 순서 → 작업자가 방향 검토 가능.
:::

#### 원칙 3: 결과를 검증

```
[수정 완료] ← 그대로 신뢰 X
       ↓
테스트 재실행
       ↓
[통과 확인] ← 작업자가 직접
```

::: aside
"수정 완료"를 그대로 신뢰하지 않음. 통과하지 않으면 디버깅 루프 한 번 더.
:::

#### 3원칙이 적용된 표준 명령

```
다음 E2E 테스트 실패 메시지를 분석해주세요:

[에러 전체 메시지를 그대로 붙여넣기]

실패 원인을 코드의 어느 부분에서 찾을 수 있는지
분석한 뒤, 수정 방안을 제시하고 적용해주세요.
수정 후 테스트를 재실행해 통과 여부를 확인해주세요.
```

#### 안티패턴 vs 3원칙

| 안티패턴 | 3원칙 적용 |
| --- | --- |
| "안 돼요 고쳐주세요" | "분석해주세요. 풀 에러 첨부" |
| "수정 끝났다고 했어요" | "재실행해 통과 확인" |

#### 무한 루프 정리 명령

같은 자리 3회 이상 맴돌면:
```
이 디버깅의 어디서 막혔는지 정리해줘.
지금까지 시도한 수정 3개와 각 수정 후의 에러를
표로 보여줘.
```

::: aside
정리된 표를 보고 작업자가 직접 판단. 에이전트가 못 푸는 문제를 작업자가 직접 본다.
:::

#### 2️⃣ 챕터 용어 해설

| 용어 | 정의 |
| --- | --- |
| Playwright | 브라우저 자동화 도구. E2E 테스트의 표준 |
| Playwright MCP | Claude Code가 Playwright를 자연어로 조작 |
| 자율 디버깅 | 에이전트가 분석·수정·재실행 반복 |
| 자율 디버깅 3원칙 | 에러 그대로, 분석 먼저, 결과 검증 |
| 무한 루프 정리 | 같은 자리 맴돌면 표로 정리해 작업자 판단 |
### 3️⃣ docs/prd.md 기반 시나리오 검증 루프

이 챕터를 학습한 뒤 다음을 할 수 있다.
- 코드 단위 검증과 시나리오 단위 검증의 차이를 안다
- scenario-verifier sub-agent의 책임을 설명한다
- 검증 루프의 반복 절차를 외운다

#### 코드 단위 vs 시나리오 단위

자료 6의 검증 vs 본 단계의 검증:

| 비교 | 코드 단위 (자료 6) | 시나리오 단위 (본 단계) |
| --- | --- | --- |
| 시점 | 코드 한 개 작성 직후 | 전체 빌드 후 |
| 단위 | 한 화면 또는 한 함수 | 사용자 시나리오 한 묶음 |
| 잡아내는 문제 | 화면별 PRD 일치 | 화면 간 연결과 흐름 |
| 본 학습 도구 | prd-reviewer 자동 (PostToolUse) | scenario-verifier 명시 호출 |

#### 세 번째 단정

> **PRD 일치성 검증은 코드 단위가 아닌 시나리오 단위로 한다. 그리고 검증은 루프로 진행한다.**

#### 코드 단위 검증의 한계

```
화면 1: PRD 일치 ✓
화면 2: PRD 일치 ✓
       ↓
하지만 화면 1 → 화면 2 라우팅이 깨져 있으면?
       ↓
시나리오 통과 X
```

::: aside
각 화면이 따로따로 PRD와 일치해도 화면 간 연결이 깨지면 시나리오는 통과 못 함. 시나리오 단위 검증이 이 문제를 잡는다.
:::

#### 검증 도구의 진화

```
[자료 3] Manyfast로 PRD 작성
       ↓
[자료 4] Manyfast → docs/prd.md export
   (Manyfast MCP 유료화로 제외)
       ↓
[자료 6] prd-reviewer가 docs/prd.md를
        Read로 직접 읽고 코드 단위 검증
       ↓
[자료 7] scenario-verifier가 docs/prd.md를
        Read로 읽고 시나리오 단위 검증
```

::: aside
본 학습 전체에서 Manyfast MCP는 PRD 작성 단계만 사용. 검증은 docs/prd.md를 직접 읽는 방식으로 일관.
:::

#### scenario-verifier sub-agent

자료 6의 prd-reviewer와 *책임 분리*된 새 sub-agent. Agent 설계 6원칙(단일 책임) 적용.

| 항목 | prd-reviewer (자료 6) | scenario-verifier (자료 7) |
| --- | --- | --- |
| 책임 | 코드 단위 검증 | 시나리오 단위 검증 |
| 호출 시점 | 코드 수정 직후 (자동) | 빌드 완료 후 (명시) |
| 입력 | 수정된 파일 1개 | 시나리오 1개 + 전체 코드베이스 |
| 출력 | 일치/불일치/검토 외 3카테고리 | 시나리오 통과/막힘 지점/수정 제안 |

#### scenario-verifier 표준 구조

```markdown
---
name: scenario-verifier
description: 빌드 완료 후 호출.
  docs/prd.md의 핵심 시나리오 1개와 전체 코드를 비교해
  시나리오가 처음부터 끝까지 통과 가능한지 검증합니다.
tools: Read, Grep, Glob
model: sonnet
---

시나리오 단위 PRD 검증 전문가의 역할.

**입력**: 검증할 시나리오 설명 1개
  (예: "셀러가 카피 입력 → 결과 확인")

**작업 절차**:
1. docs/prd.md를 Read로 읽고 시나리오 흐름 확인
2. Grep/Glob으로 시나리오 관련 파일 식별
3. 각 단계가 코드로 구현됐는지 추적
4. 화면 간 라우팅과 데이터 전달 점검
5. 막힘 지점이 있으면 구체적 위치 보고

**출력 형식** (3단 구조):
- 시나리오 통과 여부: 통과 / 부분 통과 / 미통과
- 막힘 지점: 어느 단계가 어디서 막히는지 (파일·줄)
- 수정 제안: 무엇을 추가/수정해야 하는지

**주의**:
- 수정 권한 없음 (tools에 Write/Edit 없음)
- 추측 금지. docs/prd.md와 실제 코드만 보고 판단
- 보고서는 한국어
```

#### 6원칙 적용 점검

| 원칙 | 적용 위치 |
| --- | --- |
| 1. 단일 책임 | "시나리오 단위 PRD 검증" 한 줄 |
| 2. 최소 권한 | Read, Grep, Glob만 (Write 없음) |
| 3. 결정적 출력 | 통과/막힘/제안 3단 고정 |
| 4. 책임 분리 | "수정 권한 없음" 명시 |
| 5. 호출 시점 | "빌드 완료 후 호출" |
| 6. 입출력 계약 | 시나리오 입력 → 3단 출력 |

#### 시나리오 검증 루프 (핵심)

> **본 단계의 검증은 단발 호출이 아니라 루프이다.**

흐름:
```
[1] scenario-verifier 호출 (시나리오 입력)
       ↓
[2] 보고서 수신: 통과 / 부분 통과 / 미통과
       ↓
[3] 작업자가 보고서 검증
    - 막힘 지점이 진짜인가
    - 수정 제안이 적절한가
       ↓
[4-a] 통과 → 다음 단계 (배포)
[4-b] 미통과 → 코드 수정
       ↓
[5] 코드 수정 후 다시 [1]로
       ↓
[루프 반복: 통과까지]
```

#### 검증 우선주의의 일관 적용

sub-agent 보고서도 AI 산출물.

| 점검 항목 | 방법 |
| --- | --- |
| 막힘 지점 1-2개 직접 확인 | 보고서가 가리킨 파일·줄 열어보기 |
| 수정 제안 적절성 점검 | 본인이 PRD와 대조 |
| 자동 신뢰 금지 | 환각 가능성 인식 |

#### 안티패턴 vs 검증 루프

안티패턴:
```
"보고서가 '통과'라고 했으니 다음 단계"
→ 검증 우선주의 위반
"한 번 호출하고 결과 그대로 수용"
→ 루프 누락
```

올바른 운영:
```
"보고서의 막힘 지점 1-2개 직접 확인.
 수정 후 다시 호출. 통과까지 반복."
```

#### 3️⃣ 챕터 용어 해설

| 용어 | 정의 |
| --- | --- |
| 시나리오 단위 검증 | 코드 한 줄이 아닌 사용자 흐름 한 묶음으로 검증 |
| scenario-verifier | 시나리오 단위 검증 전문 sub-agent |
| 검증 루프 | 검증 → 수정 → 재검증을 통과까지 반복 |
| PRD 일치성 | 만든 것이 PRD의 의도대로 동작하는가 |
| 두 갈래 결과 | 결과는 항상 통과 또는 미통과 (부분 통과 포함) |

### Step 2: 자율 디버깅 루프

본 단계 목표는 테스트 실패 시 자율 디버깅 3원칙 적용해 통과까지 도달.

::: aside
테스트가 처음부터 통과하면 Step 2 건너뛰고 Step 3으로. 하지만 첫 시도부터 통과하는 경우는 드뭄. 디버깅 경험이 본 단계 학습 가치.
:::

#### 2-1. 자율 디버깅 명령 (3원칙 적용)

```
다음 E2E 테스트 실패 메시지를 분석해주세요:

[에러 전체 메시지를 그대로 붙여넣기]

실패 원인을 코드의 어느 부분에서 찾을 수 있는지
분석한 뒤, 수정 방안을 제시하고 적용해주세요.
수정 후 테스트를 재실행해 통과 여부를 확인해주세요.
```

#### 2-1. 명령 점검: 3원칙

| 원칙 | 적용 위치 |
| --- | --- |
| 1. 에러 그대로 | "전체 메시지를 그대로 붙여넣기" |
| 2. 분석 먼저 | "분석한 뒤, 수정 방안 제시하고 적용" |
| 3. 결과 검증 | "재실행해 통과 여부 확인" |

#### 2-2. 에이전트의 디버깅 흐름 확인

| 단계 | 확인 |
| :---: | --- |
| 1 | 에러 분석 결과 출력 |
| 2 | 수정 방안 제시 |
| 3 | 코드 수정 적용 |
| 4 | 테스트 재실행 |
| 5 | 통과 또는 추가 수정 필요 |

#### 2-3. 무한 루프 방지

같은 자리 3회 이상 맴돌면 정리 명령:
```
이 디버깅의 어디서 막혔는지 정리해줘.
지금까지 시도한 수정과 각 수정 후의 에러를
표로 보여줘.
```

::: aside
정리된 표 보고 작업자가 직접 판단. 에이전트가 못 푸는 문제는 작업자가 직접 보기.
:::

#### 2-4. 시드 6번 흔한 디버깅 사례

사례: 시드 6번 자주 발생하는 실패와 원인.

```
[실패 1] 결과 화면에 카피 0개 표시
원인: OpenAI API 호출 실패 또는 응답 파싱 오류
수정: API 키 환경변수 확인 + 응답 구조 점검

[실패 2] 라우팅 후 빈 화면
원인: 입력값이 query 파라미터로 안 넘어감
수정: router.push에 query 추가

[실패 3] 키워드 5개 검증 통과 안 됨
원인: 빈 문자열도 5개로 카운트
수정: filter로 빈 문자열 제외 후 length 체크
```

#### Step 2 검증 기준

- [ ] 자율 디버깅 3원칙 명령을 사용했는가
- [ ] 에이전트가 분석·수정·재실행 흐름을 따랐는가

### Step 3: scenario-verifier 작성과 시나리오 검증 루프

본 단계 목표는 새 sub-agent 작성과 docs/prd.md 기반 시나리오 검증 루프 진행.

::: aside
자료 6의 prd-reviewer는 코드 단위 검증(자동). 본 단계의 scenario-verifier는 시나리오 단위 검증(명시 호출). 두 sub-agent가 역할 분리.
:::

#### 3-1. scenario-verifier.md 작성

`.claude/agents/scenario-verifier.md`:

```markdown
---
name: scenario-verifier
description: 빌드 완료 후 호출.
  docs/prd.md의 핵심 시나리오 1개와 전체 코드를 비교해
  시나리오가 처음부터 끝까지 통과 가능한지 검증합니다.
tools: Read, Grep, Glob
model: sonnet
---

시나리오 단위 PRD 검증 전문가의 역할.

**입력**: 검증할 시나리오 설명 1개

**작업 절차**:
1. docs/prd.md를 Read로 읽고 시나리오 흐름 확인
2. Grep/Glob으로 시나리오 관련 파일 식별
3. 각 단계가 코드로 구현됐는지 추적
4. 화면 간 라우팅과 데이터 전달 점검
5. 막힘 지점이 있으면 구체적 위치 보고

**출력 형식** (3단 구조):
- 시나리오 통과 여부: 통과 / 부분 통과 / 미통과
- 막힘 지점: 어느 단계가 어디서 막히는지 (파일·줄)
- 수정 제안: 무엇을 추가/수정해야 하는지

**주의**:
- 수정 권한 없음 (tools에 Write/Edit 없음)
- 추측 금지. docs/prd.md와 실제 코드만 보고 판단
- 보고서는 한국어
```

::: aside
Agent 설계 6원칙 모두 적용. 단일 책임(시나리오 검증), 최소 권한(Read/Grep/Glob), 결정적 출력(3단), 책임 분리(수정 권한 없음), 호출 시점(빌드 완료 후), 입출력 계약(본문에 명시).
:::

 표시되고, 복사 버튼을 클릭하면 카피 1개가 클립보드에 복사된다"

docs/prd.md를 읽고 현재 코드가 이 시나리오를

## Tips

### 테스트 단계 팁

#### 시나리오 통과가 동작의 진짜 정의

화면 떴다고 통과 아님. 사용자가 처음부터 끝까지 흐름 완수해야 통과.

#### E2E 통과 + scenario-verifier 통과 두 증거

E2E는 *실행 증거*, scenario-verifier는 *PRD 일치 증거*. 두 증거가 모두 있어야 다음 단계.

### Playwright MCP 팁

#### E2E 테스트 코드도 직접 안 씀

시나리오만 자연어로 말함. 위임 3원칙이 테스트 작성에도 적용.

#### Playwright MCP 연결 사전 확인

Step 0에서 미리 확인. 연결 안 되어 있으면 `claude mcp add playwright`.

### 자율 디버깅 3원칙 팁

#### 모든 에러에 적용

한 번 익히면 본 학습 후에도 평생 사용. AI 협업의 보편 패턴.

#### 에러 메시지는 정보의 보고

길고 무서워 보여도 그대로 복사. 요약 금지. 스택 트레이스가 디버깅의 핵심.

#### 무한 루프 차단

같은 자리 3회 이상 맴돌면 "어디서 막혔는지 정리해줘"부터.

### scenario-verifier 팁

#### prd-reviewer와 책임 분리

prd-reviewer는 코드 단위(자동), scenario-verifier는 시나리오 단위(명시 호출). Agent 설계 단일 책임 원칙.

#### Manyfast MCP 사용 안 함

docs/prd.md를 Read로 직접 읽음. 외부 MCP 의존 없이 작동. 자료 4-6과 일관.

#### 검증은 단발이 아닌 루프

검증 → 수정 → 재검증을 통과까지 반복. 한 번 호출하고 결과 그대로 수용 금지.

### 검증 우선주의 팁

#### sub-agent 보고도 AI 산출물

"통과"라고 적힌 보고서도 본인이 검증. 막힘 지점 1-2개를 직접 파일 열어 확인.
