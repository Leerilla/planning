# 과제: 검증된 MVP 상태로 배포 진입

## 목표

다음 학습 단계(배포) 시작 전까지 통과되는 E2E 테스트와 scenario-verifier의 통과 보고서 두 증거를 손에 쥔다. 자료 6에서 만든 화면 2개가 사용자 시나리오를 처음부터 끝까지 통과한다는 *객관 사실*을 확보한 상태로 배포에 진입한다.

다음 단계는 배포이며, 본 자료의 산출물(E2E 테스트, scenario-verifier, 검증 보고서)이 배포 결정의 근거가 된다.

---

## 산출물

### E2E 테스트

- **통과되는 E2E 테스트 1개 이상**: PRD 핵심 시나리오 기준
- Playwright MCP로 작성 (테스트 코드 직접 작성 X)
- e2e/ 폴더에 저장

### 자율 디버깅 경험

- **자율 디버깅 3원칙 적용 명령 1회 이상**
- 분석 → 수정 → 재실행 흐름 완수
- 막힘이 있었다면 docs/debug-notes.md에 메모

### scenario-verifier sub-agent

- **.claude/agents/scenario-verifier.md** 작성 완료
- Agent 설계 6원칙 모두 적용
- @scenario-verifier 호출 가능
- 책임 분리: prd-reviewer(코드 단위) vs scenario-verifier(시나리오 단위)

### 시나리오 검증 루프

- **첫 호출 보고서**: 3단 구조 (통과 여부 / 막힘 지점 / 수정 제안)
- **검증 루프 1회 이상**: 검증 → 수정 → 재검증
- **최종 통과 보고서**: "통과" 판정 + 작업자 본인 검증 완료

## 막혔을 때

| 시나리오 | 대응 |
| --- | --- |
| **Playwright MCP 연결 안 됨** | `claude mcp add playwright` 실행 후 Claude Code 재시작 |
| **E2E 테스트가 처음부터 통과** | 의외로 흔하지 않음. 시나리오가 너무 단순한 신호. 더 큰 시나리오 시도 |
| **에이전트가 에러 요약해서 답함** | 풀 메시지를 다시 강조해 붙여넣기. "전체 스택 트레이스가 필요해" |
| **무한 루프 (같은 자리 맴돔)** | "어디서 막혔는지 정리해줘" 명령. 표로 정리해 작업자가 판단 |
| **scenario-verifier 보고서가 환각** | 막힘 지점이 가리킨 파일·줄 직접 확인. 실제로 존재하는지 점검 |
| **scenario-verifier가 prd-reviewer와 겹친다고 느낌** | 두 역할 차이 재확인: prd-reviewer는 코드 단위(자동), scenario-verifier는 시나리오 단위(명시). 단일 책임 원칙 |
| **루프가 끝나지 않음** | 검증 → 수정 후 3회 이상 같은 막힘 지점 보고되면 코드의 더 근본 문제. CLAUDE.md나 docs/prd.md 자체를 점검 |

## 자율 디버깅 3원칙 표준 명령

테스트 실패 시 다음 양식 그대로 사용:

```
다음 E2E 테스트 실패 메시지를 분석해주세요:

[에러 전체 메시지를 그대로 붙여넣기]

실패 원인을 코드의 어느 부분에서 찾을 수 있는지
분석한 뒤, 수정 방안을 제시하고 적용해주세요.
수정 후 테스트를 재실행해 통과 여부를 확인해주세요.
```

세 원칙 매핑:
- 원칙 1 (에러 그대로): "전체 메시지를 그대로 붙여넣기"
- 원칙 2 (분석 먼저): "분석한 뒤, 수정 방안을 제시하고 적용"
- 원칙 3 (결과 검증): "재실행해 통과 여부를 확인"

## scenario-verifier 호출 표준 명령

```
@scenario-verifier 다음 시나리오를 검증해줘:

"[사용자가 ... 입력 → ... 클릭 → ... 표시]"

docs/prd.md를 읽고 현재 코드가 이 시나리오를
처음부터 끝까지 동작시킬 수 있는지 점검해줘.
```

응답 후 작업자 점검:
1. 막힘 지점이 가리킨 파일·줄 직접 열기
2. 진짜 문제가 있는지 본인 판단
3. 수정 제안의 적절성을 docs/prd.md와 대조
4. 수정 후 다시 @scenario-verifier 호출
5. "통과"까지 반복
