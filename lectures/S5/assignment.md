## 막혔을 때

| 시나리오 | 대응 |
| --- | --- |
| **화면 도출이 6개 이상** | 우선순위 낮은 화면을 다음 사이클로 미룸. 본 단계는 핵심 2-3개만 |
| **Task 의존성 사이클** | Task를 너무 잘게 쪼갠 신호. 1-3개 파일 단위로 다시 묶기 |
| **Stitch 시안이 PRD와 다름** | "PRD의 페르소나 기준으로 다시 만들어줘" 1회 재요청. 안 되면 시안의 핵심 구조만 참조하고 Claude Code에 PRD 명시 |
| **빌드 결과가 의도와 다름** | CLAUDE.md가 모호한 신호. 자료 4의 AI 검증 루프를 다시 한 번 돌려 점검 |
| **위임 3원칙 따랐는데 광범위한 결과** | 명령 안의 "범위" 부분 점검. "이 PR은 X 한 파일만 수정해" 명시 |
| **PR이 너무 커진다** | 한 PR에 여러 Task 묶인 신호. Task 단위로 쪼개 별도 PR로 |
| **PR이 너무 작다 (1줄 변경)** | 운영 부하만 증가. 가까운 Task와 합치기 |
| **셀프 리뷰에서 다음 Task 로직 미리 작성됨** | 에이전트가 광범위하게 만든 결과. 다음 Task로 분리하고 본 PR에서 제거 |

## 화면 분석 통과 방법

PRD 핵심 기능에서 화면을 도출하는 절차.

### 1단계: 핵심 기능 요약

Claude Code에 입력:
```
"docs/prd.md를 읽고 핵심 기능 3개를
 한 줄씩 요약해줘"
```

### 2단계: 화면 도출

```
"docs/prd.md의 핵심 기능 3개를 사용자 흐름 순서로
 화면 단위로 나눠줘.
 각 화면에 어떤 기능이 매핑되는지 명시.
 화면 개수는 3-5개를 넘기지 마."
```

### 3단계: 첫 화면 결정

| 결정 기준 | 통과 신호 |
| --- | --- |
| 페르소나 진입점 | 가장 처음 만나는 화면인가 |
| 핵심 가설 검증 | PRD 가설을 가장 빨리 시험하는 화면인가 |

### 4단계: Task 재구성

```
"위에서 도출한 화면 2개를 기준으로
 docs/tasks.md를 다시 작성해줘.
 - 화면 단위로 그룹화
 - 각 Task는 1-3개 파일 수정 단위
 - 화면 1을 먼저 완성하는 순서
 - 의존성 명시"
```

### 5단계: 합격선

- 화면 1만으로 동작 3요소 충족 가능
- 각 Task 1-3개 파일 단위
- 의존성이 사이클 없음
- 핵심 기능 3개 모두 커버

## 위임 3원칙 적용 방법

빌드 명령 작성 전 3개 질문에 답한다.

```
[1] 범위는 한 화면, 한 기능인가?
[2] 결과물이 행동과 화면 변화로 명시됐는가?
[3] 검증 방법이 사전에 정해졌는가?
```

3개 모두 "예"면 명령 발송. 한 질문이라도 "아니오"면 명령 재작성.
