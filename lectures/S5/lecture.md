# 수직 슬라이스와 위임 3원칙

수직 슬라이스는 한 기능을 UI부터 데이터까지 한 번에 만드는 빌드 방식. 모든 화면의 UI를 먼저 그린 뒤 모든 로직을 짜는 수평 슬라이스와 정반대. 본 단계 합격선은 동작하는 한 화면. 그 한 화면이 PRD의 핵심 가설을 검증하는 출발점.

본 자료는 수직 슬라이스, 위임 3원칙, Stitch와 동작 정의, 그리고 화면 분석 → Issue 등록 → 첫 PR 병합을 다룬다. 시드 6번(1인 셀러 카피 생성기) 기준. 작업 폴더는 자료 4의 planning_project 그대로 사용.

학습 목표:
- 수직 슬라이스와 수평 슬라이스의 차이 구분
- PRD 핵심 기능 3개에서 화면 도출과 Task 화면 단위 그룹화
- 위임 3원칙(범위·결과물·검증) 적용
- Stitch로 UI 시안 생성과 Claude Code 주입
- 동작 3요소(뜸·인터랙션·반응) 점검
- GitHub Issue 등록과 PR 워크플로 진입

## 이론

### 1️⃣ 수직 슬라이스란 무엇인가

이 챕터를 학습한 뒤 다음을 할 수 있다.
- 수직 슬라이스의 정의를 설명한다
- 수평 슬라이스와의 차이를 인식한다
- 수직 슬라이스의 4가지 이점을 외울 수 있다

#### 수직 슬라이스의 정의

수직 슬라이스는 **한 기능을 UI부터 로직, 데이터까지 한 번에 만드는 방식**.

::: aside
케이크에 비유하면 작은 한 조각을 통째로 자르는 모양. 위에서 아래로 모든 층을 한 번에 자르므로 한 조각만으로도 모든 맛을 느낄 수 있다.
:::

#### 수평 슬라이스의 정의

수평 슬라이스는 정반대. **모든 화면의 UI를 먼저 만들고, 모든 로직을 그 다음에 짜고, 데이터를 마지막에 연결**.

::: aside
케이크 한 층씩 자르는 모양. UI 층이 끝날 때까지 동작하는 게 없고, 로직 층이 끝날 때까지 검증할 수 없다.
:::

#### 첫 단정

> **한 기능을 UI부터 데이터까지 한 번에 만든다.**

#### 수직 슬라이스의 4가지 이점

| # | 이점 | 의미 |
| :---: | --- | --- |
| 1 | 패턴 복사 | 한 화면이 동작하면 그 패턴을 다른 화면에 복사 |
| 2 | 자신감 유지 | 동작하는 무언가가 손에 있으면 빌드 자신감 |
| 3 | 핵심 가설 검증 | PRD의 핵심 가설을 가장 빨리 검증 |
| 4 | 완성 가능성 | 짧은 빌드 시간 안에 완성 가능한 단위 |

#### 시드 6번 이점 적용

사례: 시드 6번 4가지 이점.

```
이점 1: 카피 입력 화면 동작 → 같은 패턴으로 결과 화면 만들기
이점 2: 첫 화면 떠 있는 브라우저 → 빌드 자신감 유지
이점 3: 셀러스쿨 카페 셀러에게 "이 화면 써보세요" → 가설 즉시 검증
이점 4: 한 화면 빌드 → 짧은 시간 안에 완성 가능
```

#### 수평 슬라이스의 위험

수평으로 같은 시드를 빌드하면:
- 카피 입력·결과·복사 UI를 다 그린 뒤 로직 층으로 → UI 층 끝까지 동작 없음
- 셀러에게 보여줄 수 없음
- 가설 검증이 빌드 마지막까지 미뤄짐
- PRD 변경 시 UI를 다시 그려야 함 (3개 화면 변경 비용)

#### 안티패턴 vs 수직 슬라이스

안티패턴:
```
"카피 입력, 결과, 복사 UI를 다 그렸어요.
 이제 로직을 짜야 해요"
→ 수평 슬라이스
```

수직 슬라이스:
```
"카피 입력 화면 한 개를 UI부터 데이터까지 동작시킨다.
 그 패턴을 결과 화면과 복사 화면으로 복사한다"
```

#### 수직 vs 수평 비교

| 비교 | 수직 슬라이스 | 수평 슬라이스 |
| --- | --- | --- |
| 빌드 단위 | 한 기능 통째 | 모든 화면 UI 먼저 |
| 첫 동작 시점 | 첫 기능 완료 즉시 | 모든 층 연결 후 |
| 검증 단위 | 한 기능 1개 | 전체 빌드 후 |
| 시간 안 완성 가능성 | 높음 | 낮음 |

| --- | --- |
| 수직 슬라이스 | 한 기능을 UI부터 데이터까지 한 번에 만드는 방식 |
| 수평 슬라이스 | 모든 화면을 층 단위로 만드는 방식 |
| MVP 핵심 가설 검증 | 한 화면이 동작하면 PRD 가설을 가장 빨리 알 수 있음 |
| 패턴 복사 | 첫 화면의 빌드 명령을 두 번째 화면에 90% 재사용 |
### 2️⃣ 위임 3원칙

이 챕터를 학습한 뒤 다음을 할 수 있다.
- 위임 3원칙을 외울 수 있다
- 본인 빌드 명령에 적용한다
- 광범위한 명령의 함정을 인식한다

#### AI 협업의 본질

AI 에이전트와 코드를 짜는 일의 본질은 작업자가 **직접 코드를 치는 것이 아니라 에이전트에게 일을 위임**하는 것.

위임의 품질이 결과의 품질을 결정.

::: aside
같은 화면 명령이라도 위임이 잘 된 명령은 한 번에 동작. 위임이 부족하면 매번 다른 결과.
:::

#### 두 번째 단정

> **위임 3원칙을 모든 빌드 명령에 적용한다.**

#### 위임 3원칙

| # | 원칙 | 의미 |
| :---: | --- | --- |
| 1 | 범위를 좁힌다 | 한 번에 한 화면, 한 기능 |
| 2 | 결과물을 명시한다 | 구체적 행동과 화면 변화로 |
| 3 | 검증 방법을 미리 정한다 | 무엇을 확인하면 동작인지 사전 결정 |

#### 원칙 1: 범위를 좁힌다

| 광범위 (피함) | 좁은 범위 (적정) |
| --- | --- |
| "카피 입력 + 결과 + 복사 화면 다 만들어줘" | "카피 입력 화면 한 개만. 사진 업로드, 키워드 5칸, 생성 버튼" |

::: aside
범위가 좁아지면 에이전트의 추측 여지가 줄어든다.
:::

#### 원칙 2: 결과물을 명시한다

| 모호한 결과물 (피함) | 명시된 결과물 (적정) |
| --- | --- |
| "카피 입력 기능 만들어줘" | "버튼이 클릭되면 입력값을 콘솔에 출력하고, 입력값이 비어 있으면 빨간 테두리를 표시" |

::: aside
결과물이 명시되면 의도와 결과의 차이가 좁혀진다.
:::

#### 원칙 3: 검증 방법을 미리 정한다

| 모호한 검증 (피함) | 명시된 검증 (적정) |
| --- | --- |
| "동작하면 알려줘" | "브라우저에서 사진과 키워드 5개 입력 후 버튼 누르면 콘솔에 입력값이 출력되는 것을 확인" |

::: aside
검증 방법이 사전에 정해지면 동작 여부가 명확해진다.
:::

#### 위임 3원칙 표준 양식

```
PRD의 [화면명]을 [기술 스택]으로 만들어줘.
첨부한 시안을 참조해.

기능은 다음 두 가지:
1. [입력 요소]에 입력
2. [버튼] 클릭 시 입력값을 콘솔에 출력

실제 [핵심 로직]은 다음 단계에서 추가할 거야.
```

#### 광범위한 명령의 위험

에이전트는 빠르지만 광범위한 명령에 약함.

| 항목 | 광범위한 명령 | 위임 3원칙 적용 |
| --- | --- | --- |
| 속도 | 빠름 | 비슷 |
| 결과의 일관성 | 매번 다름 | 일관됨 |
| 임의 라이브러리 추가 | 발생 | 거의 없음 |
| 검증 가능성 | 불명 | 명확 |

#### 3원칙 적용 습관 만들기

모든 빌드 명령 작성 전 3개 질문:

```
[1] 범위는 한 화면, 한 기능인가
[2] 결과물이 행동과 화면 변화로 명시됐는가
[3] 검증 방법이 사전에 정해졌는가
```

3개 모두 "예"면 명령 발송. 한 질문이라도 "아니오"면 명령 재작성.

#### 안티패턴 vs 위임 3원칙

안티패턴:
```
"카피 입력 기능 만들어줘"
→ 너무 광범위. 결과 예측 불가능
```

위임 3원칙:
```
"PRD의 카피 입력 화면 만들어줘.
 사진 업로드와 키워드 5칸에 생성 버튼만.
 실제 카피 생성 로직은 다음 단계에서"
```

#### 본 학습 전반 적용

위임 3원칙이 적용되는 곳:
- 본 단계 빌드 명령 (정식 도입)
- 다음 단계 두 번째 화면 빌드
- sub-agent 호출
- hooks 정의
- E2E 테스트 시나리오
- 배포 명령

::: aside
한 번 익히면 본 학습 후의 모든 AI 협업에 평생 사용할 수 있는 사고 방식.
:::

#### 2️⃣ 챕터 용어 해설

| 용어 | 정의 |
| --- | --- |
| 위임 | AI에게 작업을 맡기는 행위 |
| 위임 3원칙 | 범위 좁히기, 결과물 명시, 검증 방법 결정 |
| 광범위한 명령의 함정 | 에이전트가 추측해 만들고 매번 결과가 다름 |
### 3️⃣ Stitch와 동작의 정의

이 챕터를 학습한 뒤 다음을 할 수 있다.
- Stitch의 정체와 활용을 설명한다
- 동작 3요소(뜸·인터랙션·반응)를 외울 수 있다
- 동작과 예쁨을 분리한다

#### Google Stitch란

Google Labs의 AI UI 디자인 도구. 자연어로 UI 시안과 코드를 동시에 생성.

::: aside
"1인 셀러 대상 카피 입력 화면. 상품 사진 업로드 영역과 키워드 5칸, 생성 버튼, Notion 같은 미니멀 스타일"로 입력하면 시안 생성.
:::

#### Stitch와 Claude Code 연결

흐름:
```
[1] Stitch에서 시안 생성
       ↓
[2] 시안 export (이미지 또는 코드)
       ↓
[3] Claude Code에 "이 디자인대로 [기술 스택]으로 구현해줘"
       ↓
[4] 디자인의 시각 결정과 코드 구현이 분리됨
```

:::

#### 세 번째 단정

> **동작은 예쁨이 아니다. 본 단계의 합격선은 동작하는 무언가이다.**

#### 동작 3요소

| 요소 | 의미 |
| :---: | --- |
| 1 | 페이지가 브라우저에 뜬다 |
| 2 | 핵심 인터랙션이 작동한다 |
| 3 | 입력에 대한 반응이 나온다 |

세 요소가 모두 충족되면 합격.

#### 요소 1: 페이지가 뜬다

빈 화면이 아니라 디자인된 화면이 표시.

```
- CSS가 깨지지 않음
- 텍스트와 버튼이 정상적으로 보임
- 레이아웃이 무너지지 않음
```

#### 요소 2: 핵심 인터랙션 작동

```
- 버튼을 클릭할 수 있음
- 입력 필드에 텍스트를 입력할 수 있음
- 클릭이나 입력에 화면이 반응
```

#### 요소 3: 입력에 대한 반응

```
- 콘솔에 출력되거나
- 화면에 텍스트가 추가되거나
- 다른 페이지로 이동
```

::: aside
입력 후 아무 일도 일어나지 않으면 동작이 아니다.
:::

#### 합격선 범위

| 합격선 (충족 필수) | 합격선 외 (다음 단계) |
| --- | --- |
| 동작 3요소 | 디자인 미완성 |
| | 에러 처리 누락 |
| | 다른 화면 미연결 |

#### 동작과 예쁨의 분리

작업자의 함정: 디자인 정제에 시간 쏟기.

| 신호 | 본 단계 합격선과의 관계 |
| --- | --- |
| "디자인이 마음에 안 든다" | 본질 놓침 |
| "더 예쁘게 만들고 싶다" | 본질 놓침 |

::: aside
디자인은 사용자 행동 데이터 위에서 정제될 때 가장 효과적. 행동 데이터 없이 정제하면 직감 의존.
:::

#### 디자인 정제를 다음으로 미루는 이유

이중 손실 방지:
```
디자인 정제에 시간 쏟으면:
[1] 빌드 시간 부족 → 핵심 기능 미완성
[2] 정제한 디자인이 페르소나 행동과 맞지 않을 위험
```

따라서 빌드 단계에서는 **동작이 합격선**, 디자인은 시안 수준에서 멈춤.

#### 시드 6번 동작 합격선

사례: 시드 6번 첫 화면(카피 입력 화면) 합격 상태.

```
[합격 상태]
- 입력 폼이 떠 있음 (요소 1)
- 사진 업로드와 키워드 5칸 입력 가능 (요소 2)
- 생성 버튼 클릭 시 콘솔에 입력값 출력 (요소 3)

[다음 단계]
- 색상, 폰트 크기는 다음 단계 이후
- 실제 카피 생성 로직도 다음 단계
```

#### 안티패턴 vs 동작 정의

안티패턴:
```
"디자인이 마음에 안 들어요. 더 예쁘게"
→ 본 단계 본질 놓침
```

올바른 운영:
```
"본 단계 합격선은 동작하는 무언가.
 디자인 정제는 그다음"
```

#### 동작 vs 예쁨

| 비교 | 동작 (본 단계 합격선) | 예쁨 (다음 단계 이후) |
| --- | --- | --- |
| 핵심 기준 | 3요소 | 디자인 정제 |
| 시간 투자 | 짧게 | 길게 (다음 단계) |
| 검증 단위 | 핵심 인터랙션 1개 | 화면 전체 시각 품질 |

#### 1-1. 화면 분석이 필요한 이유

```
PRD는 "기능 단위"로 정의
        ↓
빌드는 "화면 단위"로 진행
        ↓
한 화면에 여러 기능 / 한 기능이 여러 화면
        ↓
이 매핑이 명확하지 않으면 매번 흔들림
```

> **화면 분석은 빌드 전의 필수 절차이다.**

#### 1-2. PRD 핵심 기능 재확인

Claude Code 명령:

기능 2 (핵심 처리): 카테고리별 차별화 카피 3개 후보 생성

## Tips

### 화면 분석 팁

#### 화면 분석은 빌드 전 필수

PRD 핵심 기능은 기능 단위이지만 빌드는 화면 단위. 매핑이 명확하지 않은 채로 빌드 시작하면 매번 흔들림.

#### 화면 개수 3-5개로 제한

본 학습 빌드 시간이 한정. 6개 이상이면 한 사이클 안에 완성 안 됨. 우선순위 낮은 화면은 다음 사이클로.

### 위임 3원칙 팁

#### 모든 빌드 명령에 적용

한 번 익히면 본 학습 내내 반복 사용. 본 학습 후에도 평생 쓸 수 있는 사고 방식.

#### 3개 질문 습관

명령 작성 전 매번:
- 범위가 한 화면, 한 기능인가
- 결과물이 명시됐는가
- 검증 방법이 사전에 정해졌는가

### 동작 정의 팁

#### 동작 3요소 외우기

뜸, 인터랙션, 반응. 디자인 미완성과 에러 처리 누락은 합격선과 무관.

#### Stitch 시안 그대로 안 옮김

시안은 참조. 실제 구현은 본인 기술 스택에 맞게 변형.

### 빌드 워크플로 팁

#### 첫 화면 동작이면 절반은 끝

두 번째 화면부터는 패턴 복사. 첫 화면 빌드 명령을 메모해두면 다음 단계 출발점.

#### 셀프 리뷰는 코드 의심하는 시간

AI가 만들었다고 그냥 통과 안 시킴. PRD와 CLAUDE.md를 직접 대조.

#### 광범위한 명령은 의도와 어긋남

"풀스택 만들어줘" 결과는 매번 다름. 위임 3원칙으로 결과를 좁힘.

### Issue·PR 팁

#### Task 1-3개 파일, PR 1-2개 파일

너무 큰 PR은 검토 불가. 너무 작은 PR은 운영 부하만 증가. 1-2개 파일이 검토 가능한 균형.

#### 화면 라벨로 진행 추적

screen-1, screen-2 라벨 등록. 화면 단위 진행 상황을 한눈에. PM이나 본인 추적 가능.

#### 수직 슬라이스로 한 화면 통째

화면 1의 Task 4개 모두 완료 → 화면 2로. 병행하면 수평 슬라이스로 변질.
